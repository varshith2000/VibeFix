# Refactoring Agent Framework — "VibeFix" Architecture Plan

The core design insight: this is **not** one smart agent doing everything. It's a **pipeline of narrow, single-responsibility agents** where every change is proposed, reviewed by independent checker agents, and only applied if it passes all gates. The system's prime directive is **behavior preservation** — the refactoring must be "sound" (prove nothing broke), not just "clean."

---

## 1. Overall Architecture (3 Layers)

```
LAYER 1: UNDERSTAND      "What is this codebase, really?"
LAYER 2: TRANSFORM       "Propose the smallest safe change set"
LAYER 3: VERIFY & EXPLAIN "Prove it's safe, apply, teach the user"
```

Plus two cross-cutting components that run through everything:

- **Orchestrator (Conductor Agent)** — framework-agnostic state machine. Holds a shared "Codebase Knowledge Graph" + "Change Ledger." Every other agent reads/writes through it. It decides what runs next, enforces budgets (max changes per run), and aborts on any gate failure.
- **Shared Context Store** — a structured, framework-agnostic artifact (JSON/graph): dependency graph, entry points, dead code map, duplication clusters, test coverage map, and the ledger of every proposed change with its rationale and verification status.

**Framework-agnostic means:** agents communicate only via structured artifacts (files/JSON/stdout contracts), never via framework-specific APIs. Each agent is a "brain + contract" — you can implement it with any LLM, and the orchestrator is a pure state machine (Python/TS), not a framework feature.

---

## 2. The Agent Roster (14 agents in 6 phases)

### PHASE A — Recon & Understanding (read-only, parallel)

**1. Cartographer Agent** — Maps the codebase: file tree, modules, entry points, languages, frameworks, build system, dependency graph (imports/requires), and boundaries. Output: the initial knowledge graph. *No opinions, just facts.*

**2. Historian Agent** — Reads git history, commit messages, TODO/FIXME/HACK comments, and README to infer **intent**: what the product is supposed to do, what the "core" is, which areas are actively churned vs. frozen. This is your "don't deviate from the product's soul" guard — the Historian produces a **Product Intent Document** that every later agent must respect.

**3. Test Surveyor Agent** — Determines what safety net exists: which test framework, coverage %, which paths are tested, and — critically — whether the project can even run/build. If tests are absent, this agent flags that Phase B must generate **characterization tests BEFORE any refactoring** (this is the key mechanism for "zero functionality change").

### PHASE B — Diagnosis (the "mess detector pool", parallel, one concern per agent)

Each produces a scored findings report; none of them change code.

**4. Architecture Auditor** — Violations of high-level principles: layering (UI calling DB directly), circular dependencies, missing separation of concerns, god files/modules, tight coupling, no clear domain boundaries.

**5. Code Smell Detector** — Function/class level: duplication (clone clusters), long functions, deep nesting, dead code, magic numbers, inconsistent naming, copy-pasted blocks across files.

**6. Consistency Sentinel** — Style and convention drift: mixed patterns (three different ways to do HTTP calls), inconsistent error handling, mixed naming conventions, config scattered everywhere, duplicate utilities.

**7. Risk Assessor** — The pessimist. For every finding from agents 4–6, it assigns a **risk score**: how likely is touching this to break behavior? Hotspots with no test coverage + high churn = "do not touch" zones. This enforces your "minimal, safe changes" requirement.

**8. Synthesis Agent (Chief Diagnostician)** — Merges all findings into one prioritized **Remediation Backlog**: each item has problem, evidence, affected files, risk score, proposed fix *category*, and expected benefit. Ranked by (impact ÷ risk). This backlog is presented to the user **before** any change is made.

### PHASE C — Safety Net Construction (before touching anything)

**9. Harness Builder Agent** — Where tests are missing, generates **characterization/snapshot tests** that pin down *current* behavior (even if current behavior is ugly). These become the ground truth: after refactoring, if these tests fail, the refactor changed behavior and gets rejected. Also pins build output, API surface (endpoints, signatures), and public exports.

### PHASE D — Transformation (sequential, one change at a time)

**10. Refactoring Engineer** — The only agent allowed to write code. Takes exactly **one backlog item**, implements it following the principle catalog (SRP, DRY, single source of truth, dependency direction, etc.), and must follow strict rules:
- Move, rename, extract, delete-dead-code — **never rewrite logic**
- One atomic change per iteration, with a diff + a plain-language rationale
- Explicitly forbidden zones from the Risk Assessor are untouchable

### PHASE E — Verification Pool (the "checks pool" you asked for — independent reviewers, parallel)

Each change must pass ALL of these before it's committed:

**11. Behavior Equivalence Verifier** — Runs the characterization suite from Phase C, diffs API surfaces/build outputs, and (where feasible) uses semantic comparison. Any behavioral delta = automatic rejection back to agent 10.

**12. Principle Compliance Reviewer** — A fresh-context agent that reviews the diff *only* for: does this actually follow the stated principle? Is it minimal (no drive-by edits)? Is naming/placement consistent with the codebase? Plays devil's advocate — it can veto with reasons.

**13. Regression Sentinel** — Runs full build + existing tests + linters/static analysis; checks for new warnings, type errors, and verifies no forbidden file was touched. Also watches cumulative budget: "we promised ≤ N changes; stop if exceeded."

### PHASE F — Explanation & Reporting (the teaching layer)

**14. Docent Agent (Explainer)** — Produces the human-facing output:
- **"State of your codebase" report**: what exists, what's missing (no tests! no error handling! everything in one file!), mapped to named software principles
- **Per-change explainers**: what was moved/renamed/extracted, *why* (which principle), what was deliberately NOT touched and why
- A before/after architecture diagram and a learning summary so the vibe coder levels up

---

## 3. The Orchestration Loop

```
1. Cartographer + Historian + Test Surveyor   (parallel, read-only)
2. Diagnosis pool: 4→5→6 parallel, → 7 Risk Assessor → 8 Backlog
3. USER CHECKPOINT: show backlog, user approves scope/risk level
4. Harness Builder pins current behavior
5. Loop over backlog items (one at a time):
      Refactoring Engineer implements
        → Verification pool (11+12+13 in parallel)
        → all pass? commit to Change Ledger : reject with reasons → retry (max 2) or defer
6. Re-run full suite → Docent produces final report + diagrams
```

Key loop properties: **single-writer** (only agent 10 writes), **fresh-context reviewers** (agents 11–13 never see the author's reasoning, so they can't be talked into approving a bad change), **retry budget** (a change that fails twice is deferred to the report, not forced), and **everything is resumable** because state lives in the shared store, not in conversation memory.

---

## 4. How Your Core Requirements Map

| Requirement | Mechanism |
|---|---|
| Don't break functionality | Characterization tests *before* refactoring + Behavior Equivalence Verifier gate |
| Don't deviate from product intent | Historian's Intent Document is a hard constraint for every downstream agent |
| Minimal changes | Risk Assessor forbidden zones + change budget + "minimal diff" check in reviewer 12 |
| Pool of checking agents, one concern each | Verification pool (11/12/13) + diagnosis pool (4/5/6) |
| Explain what/why | Docent Agent reports + per-change ledger with rationale |
| Framework/language agnostic | Agents contract via structured artifacts; orchestrator is a plain state machine |
| "What's missing" per software practices | Synthesis backlog + Docent's gap report mapped to named principles |

---

## 5. Suggested Build Order (MVP → full)

1. **MVP:** Orchestrator skeleton + Cartographer + Smell Detector + Refactoring Engineer + Behavior Verifier (run tests) + simple markdown report. This alone is useful.
2. Add Harness Builder (characterization tests) — this is what makes it *safe* rather than confident.
3. Add the diagnosis pool fully (Architecture Auditor, Consistency Sentinel, Risk Assessor) and the user checkpoint.
4. Add Principle Compliance Reviewer + Regression Sentinel (full verification pool).
5. Add Historian + Docent (intent preservation and teaching reports).
6. Later: multi-language adapters, IDE/CLI/PR-mode interfaces, incremental runs (only re-analyze changed areas).

50. If I were building it, I'd make these the non-negotiables
	1. No blind autonomous rewriting.
	2. Read-only discovery before modification.
	3. Behavioral baseline before refactoring.
	4. Every change represented as a structured proposal.
	5. Minimal-diff enforcement.
	6. Explicit file/scope permissions.
	7. Independent reviewer agents.
	8. Deterministic tests and static tooling around LLMs.
	9. Isolated Git worktrees for every change.
	10. Automatic rollback on failed verification.
	11. Human approval for high-risk changes.
	12. Complete before/after explanation.
	13. Framework-specific adapters, framework-agnostic core.
	14. Evidence store instead of agent-to-agent chat.
	15. Never force an architecture merely because it is fashionable.
	16. Preserve existing behavior unless a change is explicitly authorized.
	17. Show users what the system knows, what it suspects, and what it cannot verify.
The really interesting part is that the moat isn't the individual coding agents. Models will change rapidly. The defensible part is the system around them: repository intelligence + behavioral baselines + change contracts + minimality enforcement + independent verification + reproducible orchestration.
That is what could turn this from "another AI code fixer" into an actual software-engineering control system for vibe-coded applications.
